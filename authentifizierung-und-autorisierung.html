    8. Authentifizierung und Autorisierung

    Bei jeder Anfrage stellen sich zwei getrennte Fragen:

    • Wer ist der Benutzer? Das ist die Authentifizierung: Der Benutzer hat sich mit Benutzername und Passwort identifiziert, und jede folgende Anfrage muss belegen, dass sie von ihm stammt;
    • Hat er die Berechtigung, auf diese Seite zuzugreifen? Das ist die Autorisierung: In der Fallstudie verwaltet nur ein Benutzer mit der Rolle ADMIN Ärzte und Klienten.

    Der Identitätsnachweis muss bei jeder Anfrage mitgeliefert werden. [Symfony] speichert den angemeldeten Benutzer typischerweise in seiner Session (siehe den Abschnitt über Gültigkeitsbereiche), was die einfachste Lösung für eine Webanwendung ist. Die Fallstudie verwendet in allen ihren Versionen ([ASP.NET Core MVC], [Spring MVC], [NestJS], [Flask], [Laravel]) stattdessen ein Token (JWT, JSON Web Token), das wir auch hier verwenden werden: Nach der Anmeldung erzeugt der Server ein Token, das die Identität des Benutzers enthält, und signiert es mit einem geheimen Schlüssel (das ist das Prinzip hinter dem signierten Cookie in Beispiel 23). Das Token wird in einem Cookie gespeichert; der Browser sendet es bei jeder Anfrage zurück; der Server überprüft die Signatur. Der Benutzer kann sein Token lesen, aber nicht ändern: Jede Änderung macht die Signatur ungültig. Das Format ist standardisiert (RFC 7519), wird von allen Programmiersprachen verstanden, und das Token enthält sein Ablaufdatum. Vor allem muss der Server nichts speichern: Jeder Server, der den Schlüssel kennt, kann das Token überprüfen.

    [Symfony] verfügt über eine umfassende Sicherheitskomponente, die durch SecurityBundle integriert wird und deren Elemente wir unverändert verwenden werden:

    • Die URLs der Anwendung werden auf Firewalls (firewalls) verteilt, jede mit ihrer eigenen Methode zur Authentifizierung der Benutzer;
    • Die Authentifizierung übernehmen Authenticators (authenticators): Objekte, die bei jeder Anfrage die Identität des Benutzers bestimmen. [Symfony] bietet mehrere davon (Anmeldeformular, Session, API-Token usw.); wir schreiben unseren eigenen, der das JWT-Token liest. Der Rest der Anwendung sieht nur das Ergebnis: den authentifizierten Benutzer, bereitgestellt durch [#[CurrentUser]], [$this->getUser()] und in den Views durch [app.user];
    • Benutzer werden von einem User-Provider bereitgestellt, und ihre Passwörter werden von der Komponente PasswordHasher gehasht (Algorithmus [bcrypt]);
    • Die Autorisierung ist rollenbasiert: Der Seiten-Schutz wird durch Access-Control-Regeln beschrieben ([access_control]) oder durch das Attribut [#[IsGranted]] der Aktionen; Views prüfen ein Recht mit [is_granted];
    • Anmeldeversuche werden von der Komponente RateLimiter begrenzt (Beispiel 27).

    All das wird durch Kernel-Ereignis-Listener erreicht (vorheriges Kapitel): Die Firewall reagiert auf [kernel.request] (Priorität 8), [#[IsGranted]] wird bei [kernel.controller_arguments] gelesen, und Zugriffsverweigerungen sind Exceptions, die bei [kernel.exception] behandelt werden.

    Die Erzeugung und Überprüfung der Token übernimmt die Bibliothek [firebase/php-jwt], die am häufigsten verwendete in [PHP], installiert durch die Datei [composer.json] der Beispiele. (Es gibt ein weit verbreitetes Bundle für Token – JWT und [LexikJWTAuthenticationBundle] –, das für APIs entwickelt wurde; für eine Webanwendung genügen wenige Zeilen, und sie veranschaulichen den Mechanismus besser.)

Der Code selbst liest die Datei [.env] nicht direkt: Die Komponente [Dotenv] (Beispiel 01) hat sie in Umgebungsvariablen umgewandelt, die der Container den Services bereitstellt, die sie anfordern (das sehen wir beim Service [AuthService]). In der Produktion werden Secrets häufig dem [Symfony]-Tresor (Secrets Vault, Befehl [bin/console secrets:set]) anvertraut, der sie verschlüsselt im Projekt speichert.

use Symfony\Component\Security\Core\Exception\UserNotFoundException;

    // Wir bewahren NIEMALS ein Passwort auf, nur seinen bcrypt-Hash, ein für alle Mal berechnet
    // mit: php -r "echo password_hash('marie', PASSWORD_BCRYPT);"
    private const USERS = [
        'marie' => ['Marie Pélissier', 'USER', '$2y$10$2DnOgGBiVcyc07su9rj2E.EvOoyPFzHN/h9PLKDuoW5P7UGtclW6W'],

    public function find(string $login): ?User
    {
        if (! isset(self::USERS[$login])) {
            return null;
        }
        [$name, $role, $hash] = self::USERS[$login];
        return new User($login, $name, $role, $hash);
    }

    // die drei Methoden von UserProviderInterface
    public function loadUserByIdentifier(string $identifier): UserInterface
    {
        return $this->find($identifier) ?? throw new UserNotFoundException();
    }

    // der in der Session gespeicherte Benutzer, der neu geladen werden soll: hier nie aufgerufen,
    // da die Firewall stateless ist
    public function refreshUser(UserInterface $user): UserInterface
    {
        throw new UnsupportedUserException();
    }

    public function supportsClass(string $class): bool
    {
        return $class === User::class;
    }

    • Zeilen 17–20: zwei fest codierte Testbenutzer (Beispiel 28 und die Fallstudie speichern sie in einer Datenbank): für jeden Login der Name, die Rolle und der Passwort-Hash. Der Hash wird mit dem Algorithmus bcrypt erzeugt, der für Passwörter entwickelt wurde. Er hat zwei besondere Eigenschaften. Er ist absichtlich langsam, mit einstellbarem Grad der Langsamkeit (der Kostenfaktor, hier auf 10 gesetzt: 2^10 Rechenzyklen, daraus ergibt sich der Hash [$10$]): wenige Dutzend Millisekunden, für einen Benutzer nicht wahrnehmbar, die es für einen Angreifer aber sehr teuer machen, Milliarden von Passwörtern auszuprobieren. Er ist gesalzen: Ein zufällig erzeugtes Salt wird vor dem Hashen mit dem Passwort vermischt und im Hash selbst gespeichert (die 22 Zeichen nach [$10$]); zwei Benutzer mit demselben Passwort haben somit unterschiedliche Hashes. Die Hashes wurden einmalig mit der Funktion [password_hash] von [PHP] (Zeile 16) oder mit dem Befehl [bin/console security:hash-password] von [Symfony] berechnet: Sie bei jeder Anfrage neu zu berechnen wäre unnötige Zeitverschwendung, da die Anwendung bei jeder Anfrage neu aufgebaut wird. [bcrypt] berücksichtigt nur die ersten 72 Bytes eines Passworts: Die Fallstudie trägt dem Rechnung;

    <?php
// src/Security/AuthService.php: die Prüfung der Passwörter und der JWT-Tokens

namespace App\Security;

use Firebase\JWT\JWT;
use Firebase\JWT\Key;
use Symfony\Component\DependencyInjection\Attribute\Autowire;
use Symfony\Component\PasswordHasher\Hasher\UserPasswordHasherInterface;
use Throwable;

class AuthService
{
    // der Name des Cookies, das das Token trägt
    public const COOKIE = 'token';

    public function __construct(
        private UsersService $users,
        // der Service zum Hashing der Passwörter (siehe config/packages/security.yaml)
        private UserPasswordHasherInterface $hasher,
        // #[Autowire(env: ...)]: der Wert einer Umgebungsvariable (Datei .env);
        // das Präfix int: wandelt ihn in eine Ganzzahl um
        #[Autowire(env: 'JWT_SECRET')] private string $secret,
        #[Autowire(env: 'int:JWT_DURATION_MINUTES')] public readonly int $durationMinutes,
    ) {
    }

    // der Benutzer oder null, wenn das Login unbekannt oder das Passwort falsch ist.
    // isPasswordValid hasht das eingegebene Passwort mit dem Salt des gespeicherten Hashs
    // und vergleicht dann die beiden Ergebnisse
    public function validate(?string $login, ?string $password): ?User
    {
        if (! $login || $password === null) {
            return null;
        }
        $user = $this->users->find($login);
        if ($user === null || ! $this->hasher->isPasswordValid($user, $password)) {
            return null;
        }
        return $user;
    }

    // das JWT-Token des Benutzers, signiert mit dem geheimen Schlüssel (HMAC-SHA256)
    public function createToken(User $user): string
    {
        $now = time();
        // der Inhalt des Tokens: die „Claims“ (Aussagen über den Benutzer)
        $claims = [
            'sub' => $user->login,
            'name' => $user->name,
            'role' => $user->role,
            'iat' => $now,
            'exp' => $now + $this->durationMinutes * 60,
        ];
        return JWT::encode($claims, $this->secret, 'HS256');
    }

    // der durch ein Token beschriebene Benutzer, dessen Signatur und Ablaufdatum
    // gültig sind; sonst null (gefälschtes, abgelaufenes oder unlesbares Token)
    public function check(string $token): ?User
    {
        try {
            // decode gibt ein Objekt zurück; (array) wandelt es in ein assoziatives Array um
            $claims = (array) JWT::decode($token, new Key($this->secret, 'HS256'));
        } catch (Throwable) {
            return null;
        }
        return new User($claims['sub'], $claims['name'], $claims['role'], claims: $claims);
    }
}
    • Zeilen 17–26: Der Service erhält den User Provider, den Service zum Hashen von Passwörtern ([UserPasswordHasherInterface], der den in [security.yaml] gewählten Algorithmus anwendet) sowie zwei Konfigurationswerte. Das Attribut [#[Autowire(env: 'NAME')]] liefert den Wert einer Umgebungsvariablen; ein Präfix konvertiert ihn: [int:] in eine Ganzzahl (es gibt weitere: [bool:], [json:], [base64:] ...). Die Gültigkeitsdauer ist eine öffentliche schreibgeschützte Eigenschaft: Der Controller wird sie verwenden;
    • Zeilen 31–41: Überprüfung von Benutzername und Passwort. [isPasswordValid] hasht das eingegebene Passwort mit dem Salt des gespeicherten Hashs und vergleicht die beiden Hashes. Ein unbekannter Benutzername und ein falsches Passwort führen zum selben Ergebnis, [null];
    • Zeilen 44–56: Erzeugung des Tokens. Das Token enthält ein Array von Aussagen (Claims) über den Benutzer. Einige haben standardisierte Namen: [sub] (subject), die ID des Benutzers; [iat] (issued at), das Erstellungsdatum; [exp] (expiration), das Ablaufdatum. Die Datumsangaben sind in Sekunden seit dem 1. Januar 1970 ausgedrückt (die Funktion [time()] von [PHP]). Die übrigen Felder sind optional: hier der Name und die Rolle. [JWT::encode] erzeugt das Token und signiert es mit dem Algorithmus [HS256] (HMAC-SHA256, eine Signatur mit einem gemeinsamen geheimen Schlüssel);

// src/Security/TokenAuthenticator.php: der AUTHENTICATOR der Firewall (siehe
// config/packages/security.yaml): Bei jeder Anfrage stellt er fest, wer der Benutzer ist,
// anhand des JWT-Tokens im Cookie [token]

namespace App\Security;

use Symfony\Component\HttpFoundation\RedirectResponse;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Security\Core\Authentication\Token\TokenInterface;
use Symfony\Component\Security\Core\Exception\AuthenticationException;
use Symfony\Component\Security\Core\Exception\CustomUserMessageAuthenticationException;
use Symfony\Component\Security\Http\Authenticator\AbstractAuthenticator;
use Symfony\Component\Security\Http\Authenticator\Passport\Badge\UserBadge;
use Symfony\Component\Security\Http\Authenticator\Passport\Passport;
use Symfony\Component\Security\Http\Authenticator\Passport\SelfValidatingPassport;
use Symfony\Component\Security\Http\EntryPoint\AuthenticationEntryPointInterface;

class TokenAuthenticator extends AbstractAuthenticator implements AuthenticationEntryPointInterface
{
    public function __construct(private AuthService $auth)
    {
    }

    // Der Authenticator wird nur aktiv, wenn die Anfrage das Token-Cookie trägt;
    // andernfalls bleibt der Besucher anonym
    public function supports(Request $request): ?bool
    {
        return $request->cookies->has(AuthService::COOKIE);
    }

    // der PASSPORT des Benutzers: wer er ist (das Badge) und wie das zu prüfen ist.
    // Das Token wurde bereits geprüft: Der Passport validiert sich selbst (SelfValidatingPassport)
    public function authenticate(Request $request): Passport
    {
        $user = $this->auth->check($request->cookies->get(AuthService::COOKIE));
        if ($user === null) {
            throw new CustomUserMessageAuthenticationException('invalid token');
        }
        // das Badge: das Login und eine Funktion, die den Benutzer zurückgibt (hier den aus dem
        // Token, ohne die Liste der Benutzer zu konsultieren)
        return new SelfValidatingPassport(new UserBadge($user->login, fn () => $user));
    }

    // ein gültiges Token: null, die Anfrage setzt ihren Weg zur Action fort
    public function onAuthenticationSuccess(Request $request, TokenInterface $token, string $firewallName): ?Response
    {
        return null;
    }

    // ein ungültiges Token (abgelaufen, gefälscht): ab zu /login, und wir löschen das Cookie
    public function onAuthenticationFailure(Request $request, AuthenticationException $exception): ?Response
    {
        $response = new RedirectResponse('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }

    // der ENTRY POINT: die Antwort an einen anonymen Besucher, der eine
    // geschützte Seite anfordert; hier eine Weiterleitung auf die Login-Seite
    public function start(Request $request, ?AuthenticationException $authException = null): Response
    {
        return new RedirectResponse('/login');
    }
}

    Für jede Anfrage, die die Firewall durchläuft, ruft [Symfony] die Methoden des Authenticators in dieser Reihenfolge auf:

    • Zeilen 28–31: [supports]: Ist der Authenticator an dieser Anfrage beteiligt? Ja, wenn sie das Token-Cookie enthält. Andernfalls geschieht nichts: Der Besucher bleibt anonym;
    • Zeilen 35–44: [authenticate] erstellt einen Passport: die Identität des Benutzers (ein Badge, [UserBadge]) und die zu überprüfenden Nachweise. Ein klassisches Anmeldeformular würde das eingegebene Passwort in den Passport aufnehmen, das [Symfony] selbst überprüfen würde. Hier ist der Nachweis das Token, das bereits von [AuthService] überprüft wurde: Der Passport validiert sich selbst ([SelfValidatingPassport]). Das Badge enthält den Login und eine Funktion, die den Benutzer identifiziert: hier den im Token beschriebenen Benutzer, ohne die Benutzerliste zu befragen (ohne diese Funktion würde [Symfony] den Benutzer beim Provider anfordern). Ein ungültiges Token löst eine Authentifizierungs-Exception aus;
    • Zeilen 47–50: [onAuthenticationSuccess]: Die Authentifizierung war erfolgreich. Die Rückgabe von [null] lässt die Anfrage mit einem authentifizierten Benutzer zur Action durch. (Ein Anmeldeformular würde hier auf die Startseite umleiten);
    • Zeilen 53–58: [onAuthenticationFailure]: Die Authentifizierung ist fehlgeschlagen (Token abgelaufen oder gefälscht). Die Antwort leitet auf die Anmeldeseite um und nutzt die Gelegenheit, das Cookie zu löschen: [clearCookie] fügt der Antwort ein leeres, bereits abgelaufenes Cookie hinzu;
    • Zeilen 62–65: [start] ist die Methode der Schnittstelle [AuthenticationEntryPointInterface]: der Einstiegspunkt der Firewall, d. h. die Antwort, die an einen anonymen Besucher gesendet wird, der eine geschützte Seite anfordert. Hier ist das eine Umleitung auf die Anmeldeseite.

    Der Authenticator verweigert keinen Zugriff: Er stellt fest, wer der Benutzer ist, oder dass der Benutzer anonym ist. Das ist die Authentifizierung. Verweigerungen sind Sache der Zugriffskontrolle.

namespace App\Controller;

use App\Security\AuthService;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\Routing\Attribute\Route;

class AuthController extends AbstractController
{
    public function __construct(private AuthService $auth)
    {
    }

    #[Route('/', methods: ['GET'])]
    public function home(): Response
    {
        return $this->redirect('/profile');
    }

    #[Route('/login', methods: ['GET'])]
    public function form(): Response
    {
        return $this->render('auth/login.html.twig');
    }

    #[Route('/login', methods: ['POST'])]
    public function login(Request $request): Response
    {
        // das Anti-CSRF-Token des Formulars (siehe Beispiel 21)
        if (! $this->isCsrfTokenValid('login', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $login = $request->getPayload()->getString('login');
        $user = $this->auth->validate($login, $request->getPayload()->getString('password'));
        if ($user === null) {
            // eine bewusst vage Meldung: Wir sagen nicht, ob es das Login oder das Passwort ist
            return $this->render('auth/login.html.twig', ['login' => $login,
                'error' => 'Incorrect login or password.']);
        }
        // das Token in einem Cookie: Das JavaScript der Seite kann es nicht lesen
        // (httpOnly); es wird nicht mit POST-Anfragen von anderen Websites gesendet
        // (sameSite); es verschwindet gleichzeitig mit dem Ablauf des Tokens
        $response = $this->redirect('/profile');
        $response->headers->setCookie(Cookie::create(AuthService::COOKIE, $this->auth->createToken($user))
            ->withExpires(time() + $this->auth->durationMinutes * 60)
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $response;
    }

    // Abmelden: nur per POST (ein einfacher Link, der auf einer anderen Website platziert ist, kann
    // den Benutzer nicht ohne sein Wissen abmelden); wir löschen das Cookie
    #[Route('/logout', methods: ['POST'])]
    public function logout(Request $request): Response
    {
        if (! $this->isCsrfTokenValid('logout', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $response = $this->redirect('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }
}

    • Zeilen 40–45: der Anmeldevorgang. Schlägt er fehl, wird das Formular mit dem eingegebenen Benutzernamen und einer bewusst vagen Meldung erneut angezeigt: Die Meldung „unbekannter Benutzername“ würde einem Angreifer verraten, welche Benutzernamen existieren;
    • Zeilen 49–54: Bei Erfolg wird das Token in einem Cookie gespeichert, und der Benutzer wird auf die geschützte Seite umgeleitet (PRG-Schema). Das Cookie ist [httpOnly]: Das [JavaScript] der Seite kann es nicht lesen, was das Token vor Skriptinjektion (XSS) schützt; es ist [SameSite=Lax]: Der Browser sendet es nicht bei einer POST-Anfrage mit, die von einer anderen Website stammt, was die Anwendung vor CSRF-Angriffen schützt; sein Ablaufdatum ([withExpires], hier eine Anzahl von Sekunden seit 1970) entspricht dem des Tokens. In der Produktion würden wir bei HTTPS [withSecure(true)] ergänzen: Das Cookie würde dann niemals über eine unverschlüsselte Verbindung gesendet;
    • Zeilen 59–68: Das Abmelden löscht das Cookie ([clearCookie]). Dies ist eine POST-Action, die durch ein Anti-CSRF-Token geschützt ist: Ein einfacher Link auf [/logout], der auf einer anderen Website oder in einem Bild platziert ist, kann den Benutzer nicht ohne sein Wissen abmelden. Beachten Sie eine Einschränkung von Tokens: Das Token selbst bleibt bis zu seinem Ablauf gültig. Wer eine Kopie davon angefertigt hat, könnte es weiterhin verwenden. Deshalb ist ihre Lebensdauer begrenzt.

        foreach (str_split($text) as $i => $character) {

            $angle = self::random(-0.35, 0.35);   // Rotation im Bogenmaß (etwa ±20°)

                    implode(' ', $d), self::color(), self::random(2.2, 3));

// src/Security/CaptchaService.php: die ausstehenden CAPTCHAs, vom Server im
// Cache aufbewahrt (siehe Beispiel 20)

namespace App\Security;

use Psr\Cache\CacheItemPoolInterface;

class CaptchaService
{
    // die Lebensdauer eines CAPTCHA, in Sekunden
    private const LIFETIME = 600;

    public function __construct(private CacheItemPoolInterface $cache)
    {
    }

    public function generate(): Captcha
    {
        $text = CaptchaDrawing::randomText(5);
        // ein zufälliger, nicht erratbarer Bezeichner: 12 Bytes, von einem
        // kryptografischen Generator gezogen (random_bytes), hexadezimal geschrieben (bin2hex)
        $id = bin2hex(random_bytes(12));
        // die erwartete Antwort im Cache, für 10 Minuten (expiresAfter): Der
        // Cache vergisst sie danach von selbst
        $item = $this->cache->getItem("captcha.$id");
        $this->cache->save($item->set($text)->expiresAfter(self::LIFETIME));
        return new Captcha($id, CaptchaDrawing::svg($text));
    }

    // Das CAPTCHA wird in jedem Fall VERBRAUCHT: Ein Bild wird nur einmal verwendet
    public function check(?string $id, ?string $answer): bool
    {
        // Ein fehlerhaft aufgebauter Bezeichner kann kein Schlüssel des Caches sein
        if ($id === null || ! ctype_xdigit($id) || $answer === null) {
            return false;
        }
        $item = $this->cache->getItem("captcha.$id");
        // deleteItem: Die Antwort wird aus dem Cache entfernt, ob sie richtig ist oder nicht
        $this->cache->deleteItem("captcha.$id");
        if (! $item->isHit()) {
            return false;    // unbekannter Bezeichner oder abgelaufenes CAPTCHA
        }
        // strcasecmp gibt 0 für zwei gleiche Strings zurück, ohne Beachtung der Groß-/Kleinschreibung
        return strcasecmp($item->get(), trim($answer)) === 0;
    }
}
    • Zeilen 18–29: ein neues CAPTCHA: ein zufälliger Text, ein zufälliger, nicht erratbarer Bezeichner und das Bild. Zu jedem Bezeichner speichert der Server die erwartete Antwort zehn Minuten lang im Cache (Beispiel 20): Die Methode [expiresAfter] des Cache-Elements legt dessen Lebensdauer in Sekunden fest. Nach Ablauf dieser Zeit verwirft der Cache es automatisch. Die Seite erhält nur den Bezeichner und das Bild: Die Antwort verlässt den Server nie;
    • Zeilen 32–46: die Validierung. Der Bezeichner stammt vom Client: Wir prüfen zuerst, ob er aus Hexadezimalziffern besteht ([ctype_xdigit]), da bestimmte Zeichen ([{}()/\@:]) in Cache-Schlüsseln verboten sind und eine Exception auslösen würden. Das Element wird gelesen und dann aus dem Cache entfernt ([deleteItem]): Das CAPTCHA wird in jedem Fall verbraucht, ob erfolgreich oder nicht. Ohne dies könnte ein Programm alle möglichen Antworten für dasselbe Bild ausprobieren. Der Vergleich ignoriert die Groß- und Kleinschreibung ([strcasecmp] liefert 0 für zwei gleiche Zeichenketten, unabhängig von Groß- und Kleinbuchstaben) und Leerzeichen um die Eingabe ([trim]).

// src/Controller/AuthController.php: Login (mit CAPTCHA und Begrenzung der

namespace App\Controller;

use App\Security\AuthService;
use App\Security\CaptchaService;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\RateLimiter\RateLimiterFactoryInterface;
use Symfony\Component\Routing\Attribute\Route;

class AuthController extends AbstractController
{
    // $loginLimiter: die Factory des Limiters [login] (siehe config/packages/framework.yaml);
    // der Name des Parameters bezeichnet den Limiter
    public function __construct(
        private AuthService $auth,
        private CaptchaService $captchas,
        private RateLimiterFactoryInterface $loginLimiter,
    ) {
    }

    #[Route('/', methods: ['GET'])]
    public function home(): Response
    {
        return $this->redirect('/profile');
    }

    #[Route('/login', methods: ['GET'])]
    public function form(): Response
    {
        return $this->loginPage();
    }

    #[Route('/login', methods: ['POST'])]
    public function login(Request $request): Response
    {
        $inputs = $request->getPayload();
        if (! $this->isCsrfTokenValid('login', $inputs->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $login = $inputs->getString('login');
        // der Limiter DIESES Clients: Der Schlüssel seines Fehlerzählers ist seine IP-Adresse
        $limiter = $this->loginLimiter->create($request->getClientIp());

        // 1. Auf eine gesperrte Adresse wird gar nicht erst gehört; consume(0) fragt den
        // Zähler ab, ohne etwas zu verbrauchen
        $state = $limiter->consume(0);
        if ($state->getRemainingTokens() === 0) {
            $seconds = $state->getRetryAfter()->getTimestamp() - time();
            return $this->loginPage($login, "Too many attempts: try again in $seconds s.");
        }
        // 2. zuerst das CAPTCHA (billig), danach das Passwort (bcrypt, teuer);
        // consume(): ein weiterer Fehlversuch
        if (! $this->captchas->check($inputs->getString('captchaId'), $inputs->getString('captcha'))) {
            $limiter->consume();
            return $this->loginPage($login, 'The image code is incorrect.');
        }
        $user = $this->auth->validate($login, $inputs->getString('password'));
        if ($user === null) {
            $limiter->consume();
            return $this->loginPage($login, 'Incorrect login or password.');
        }
        // Ein erfolgreiches Login löscht die Fehlversuche
        $limiter->reset();
        $response = $this->redirect('/profile');
        $response->headers->setCookie(Cookie::create(AuthService::COOKIE, $this->auth->createToken($user))
            ->withExpires(time() + $this->auth->durationMinutes * 60)
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $response;
    }

    #[Route('/logout', methods: ['POST'])]
    public function logout(Request $request): Response
    {
        if (! $this->isCsrfTokenValid('logout', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $response = $this->redirect('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }

    // Jede Anzeige des Formulars baut ein NEUES CAPTCHA
    private function loginPage(?string $login = null, ?string $error = null): Response
    {
        return $this->render('auth/login.html.twig', ['login' => $login, 'error' => $error,
            'captcha' => $this->captchas->generate()]);
    }
}
    • Zeilen 21–26: Der Controller erhält die Factory für den Limiter [login];
    • Zeile 49: der Limiter dieses Clients, [create(key)], liefert einen Limiter, der unter diesem Schlüssel einen eigenen Zähler hat – hier die IP-Adresse des Clients ([getClientIp()]);
    • Zeilen 53–57: Eine gesperrte Adresse wird gar nicht erst angehört. [consume(0)] fragt den Limiter ab, ohne etwas zu verbrauchen; das zurückgegebene Objekt [RateLimit] liefert die Anzahl der verbleibenden Tokens ([getRemainingTokens()]) und den Zeitpunkt, ab dem die Aktion wieder erlaubt ist ([getRetryAfter()]), woraus sich die Anzahl der Sekunden ableiten lässt, die zu warten sind;
    • Zeilen 60–68: Das CAPTCHA wird vor dem Passwort überprüft; seine Überprüfung kostet fast nichts, während [bcrypt] absichtlich langsam ist. Ein Programm, das ein falsches CAPTCHA eingibt, würde daher [bcrypt] nicht auslösen. Jeder Fehlschlag – sei es beim CAPTCHA oder beim Passwort – verbraucht ein Token ([consume()], das standardmäßig eines verbraucht). Nach dem dritten Fehlschlag ist kein Token mehr übrig: Die Adresse ist bis zum Ende des 60-Sekunden-Fensters gesperrt, gezählt ab dem ersten Fehlschlag;
    • Zeile 70: Eine erfolgreiche Anmeldung setzt die fehlgeschlagenen Versuche zurück ([reset()]);
    • Zeilen 91–95: Bei jeder Anzeige des Formulars wird ein neues CAPTCHA erzeugt, auch nach einem fehlgeschlagenen Versuch.

    Das SecurityBundle bietet außerdem eine eingebaute Begrenzung der Anmeldeversuche (die Firewall-Option [login_throttling] ), die für seine eigenen Login-Authenticators ([form_login] ...) gilt, nicht für unsere Action. Um die Anzahl der Anfragen für eine Route zu begrenzen, würden wir einen Limiter auf dieselbe Weise verwenden, entweder innerhalb der Action oder in einem Listener für [kernel.request]. Wir haben uns entschieden, nur die fehlgeschlagenen Versuche zu zählen, um einen Benutzer, der sich normal anmeldet, nicht zu behindern.
