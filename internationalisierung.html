    5. Internationalisierung

    Eine internationalisierte Anwendung zeigt ihre Texte in der Sprache des Benutzers an. Die Fallstudie ist auf Französisch und Englisch verfügbar. Das Prinzip ist einfach: Die Views enthalten keinen Text mehr, sondern Schlüssel ([MENU.HOME]), und ein Wörterbuch pro Sprache ordnet jedem Schlüssel einen Text zu. Die gewählte Sprache wird in einem Cookie gespeichert.

    [Symfony] enthält eine Übersetzungskomponente, den Translator, dem wir bereits in Beispiel 09 bei den Validierungsmeldungen begegnet sind. Seine Wörterbücher liegen im Ordner [translations], mit einer Datei pro Domäne und Sprache: [validators.en.yaml] (die Domäne der Validierungsmeldungen, Beispiel 09), [messages.en.yaml] (die Standarddomäne, die für unsere Texte). Das YAML-Format erlaubt verschachtelte Schlüssel: So sind die Wörterbücher der Versionen [ASP.NET Core MVC], [NestJS], [Spring MVC], [Flask] und [Laravel] der Fallstudie aufgebaut, abgesehen von der Syntax. Für die Syntax der Meldungen selbst wählen wir das ICU-Format (International Components for Unicode), einen Standard, den die Erweiterung [intl] von [PHP] interpretieren kann und der beispielsweise Text in die Pluralform flektieren kann. Die Formatierung von Daten und Beträgen bleibt dieselbe wie in Beispiel 16.

    Der Dateiname besteht aus drei Teilen: der Domäne ([messages], die Standarddomäne), dem Suffix [+intl-icu], das Meldungen im ICU-Format kennzeichnet, und der Sprache ([fr]). Die Schlüssel werden mithilfe der YAML-Verschachtelung nach Themen gruppiert: Der Menüeintrag „Accueil“ hat den Schlüssel [MENU.HOME], wobei die Ebenen durch einen Punkt getrennt sind. Ein Text kann Parameter enthalten, geschrieben als [{name}], die bei der Übersetzung ersetzt werden.

    • Zeile 9: Apostrophe begrenzen einen YAML-String; sie sind notwendig, wenn der Text Zeichen enthält, die YAML interpretiert (geschweifte Klammern, Doppelpunkte usw.);
    • Zeile 15: eine Plural-Meldung. [{n, plural, ...}] wählt anhand des Werts des Parameters [n] eine Form aus: [=0] für genau 0, [one] für den Singular, [other] für den Plural; [#] wird durch die Zahl ersetzt. Die Pluralregeln hängen von der Sprache ab, und ICU kennt sie: Im Französischen sind 0 und 1 Singular, im Englischen dagegen ist 0 Plural („0 products“). Das ist eine Verbesserung gegenüber dem „product(s)“ aus früheren Versionen der Fallstudie.

    <?php
// src/EventListener/SetLanguage.php: die Sprache jeder Anfrage

namespace App\EventListener;

use Symfony\Component\EventDispatcher\Attribute\AsEventListener;
use Symfony\Component\HttpKernel\Event\RequestEvent;
use Symfony\Component\HttpKernel\KernelEvents;

// Priorität 20: nach dem Routing, vor den Listenern von Symfony, die die Sprache verwenden (siehe Beispiel 16)
#[AsEventListener(event: KernelEvents::REQUEST, priority: 20)]
class SetLanguage
{
    // die unterstützten Sprachen; die erste ist die Standardsprache
    public const LANGUAGES = ['en', 'fr'];

    public const COOKIE = 'language';

    // die Sprache des Cookies [language], falls sie unterstützt wird, sonst Englisch
    public function __invoke(RequestEvent $event): void
    {
        $request = $event->getRequest();
        $language = $request->cookies->get(self::COOKIE);
        $request->setLocale(in_array($language, self::LANGUAGES, true) ? $language : self::LANGUAGES[0]);
    }
}

    Dies ist der [SetLanguage]-Listener aus Beispiel 16, der die Sprache diesmal aus einem Cookie bezieht:

    • Zeile 11: der [kernel.request]-Ereignis-Listener mit Priorität 20: nach dem Routing, aber vor den [Symfony]-Listenern, die die Sprache der Anfrage verwenden (Beispiel 16);
    • Zeilen 15–17: die unterstützten Sprachen und der Cookie-Name: öffentliche Klassenkonstanten, die aus anderen Klassen zugänglich sind ([SetLanguage::LANGUAGES]);
    • Zeilen 22–24: die Sprache der Anfrage: die Sprache des [language]-Cookies, sofern vorhanden und unterstützt; andernfalls Englisch. [$request->cookies] ist die Menge der vom Browser gesendeten Cookies (Beispiel 05); [get] liefert den Wert eines Cookies oder [null]. [in_array] vergleicht mit [true] als drittem Parameter auch die Typen ([===]). [setLocale] legt die Sprache der Anfrage fest: Das ist die Sprache, die der Translator, unsere Formatierungsfilter und der Filter [format_currency] von [Twig] verwenden.

    Anders als [Laravel] verschlüsselt [Symfony] Cookies nicht: Das Cookie [language] wird im Klartext übertragen. Das ist unproblematisch: Es enthält keine vertraulichen Informationen, und der Server akzeptiert nur unterstützte Sprachen. Das folgende Beispiel greift die Frage wieder auf, wie viel Vertrauen man einem Cookie schenken kann.

    <?php
// src/Controller/LanguageController.php: die Wahl der Sprache

namespace App\Controller;

use App\EventListener\SetLanguage;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\RedirectResponse;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\Routing\Attribute\Route;

class LanguageController extends AbstractController
{
    // GET /language/fr: speichert die Wahl in einem Cookie und kehrt dann zur vorherigen Seite zurück.
    // requirements: Eine andere Sprache als en oder fr passt nicht zur Route (404)
    #[Route('/language/{code}', name: 'language', requirements: ['code' => 'en|fr'], methods: ['GET'])]
    public function change(Request $request, string $code): RedirectResponse
    {
        $response = $this->redirect(self::originPage($request));
        // das Cookie: ein Jahr Lebensdauer, vom JavaScript der Seite nicht lesbar (httpOnly),
        // nie mit einer POST-Anfrage von einer anderen Website gesendet (sameSite lax)
        $response->headers->setCookie(Cookie::create(SetLanguage::COOKIE, $code)
            ->withExpires(new \DateTimeImmutable('+1 year'))
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $response;
    }

    // die Seite, von der wir kommen (Header Referer), von der wir nur den Pfad behalten:
    // Eine Weiterleitung auf eine vollständige, aus der Anfrage stammende Adresse würde es erlauben,
    // den Benutzer auf eine andere Website zu schicken (Schwachstelle „Open Redirect“)
    private static function originPage(Request $request): string
    {
        // parse_url zerlegt eine URL in ihre Bestandteile (Pfad, Parameter...)
        $url = parse_url($request->headers->get('Referer', ''));
        $path = $url['path'] ?? '';
        // "//site.com/..." würde vom Browser als Adresse
        // auf einer ANDEREN Website verstanden: ebenfalls abgelehnt
        if (! str_starts_with($path, '/') || str_starts_with($path, '//')) {
            return '/';
        }
        return isset($url['query']) ? "$path?{$url['query']}" : $path;
    }
}
    • Zeile 17: die Route [/language/{code}]. Die Option [requirements] (Beispiel 02) beschränkt den Parameter auf die beiden unterstützten Sprachen: [/language/de] entspricht keiner Route und liefert einen 404-Fehler;
    • Zeile 20: Die Aktion antwortet mit einer Weiterleitung auf die Seite, von der der Benutzer kam: Der Benutzer wird in der neuen Sprache auf seine Seite zurückgeführt;
    • Zeilen 23–26: Die Antwort enthält ein Cookie, das der Browser bei jeder Anfrage zurücksendet. Die Klasse [Cookie] von [Symfony] beschreibt es: [Cookie::create(name, value)] erstellt es, und jede Methode von [with...] liefert eine veränderte Kopie (ein unveränderliches Objekt; siehe Beispiel 03): [withExpires], das Ablaufdatum (in einem Jahr); [withHttpOnly(true)] macht es für das [JavaScript] auf der Seite unsichtbar; [withSameSite(Cookie::SAMESITE_LAX)] verhindert, dass der Browser es mit einer POST-Anfrage von einer anderen Website sendet. ([httpOnly] und [lax] sind übrigens die Standardwerte von [Cookie::create].) [$response->headers->setCookie] fügt es der Antwort als [Set-Cookie]-Header hinzu;
    • Zeilen 33–44: Die ursprüngliche Seite wird durch den Header [Referer] in der Anfrage angegeben (die falsch geschriebene Variante mit nur einem [r] ist die im HTTP-Standard verwendete), den der Browser mit der URL der Seite befüllt, die den Link enthielt. Dieser Header stammt jedoch vom Client, der beliebige Inhalte hineinschreiben kann. Blind auf diese Adresse weiterzuleiten, würde unsere Anwendung zu einem Open Redirect machen: Ein bösartiger Link mit unserem Domainnamen könnte den Benutzer auf eine schädliche Website schicken. Deshalb behalten wir nur den Pfad und die Parameter der URL (die Funktion [parse_url] von [PHP] zerlegt sie in einem assoziativen Array in ihre Bestandteile) und weisen jeden Pfad zurück, der mit [//] beginnt, was der Browser als Adresse einer anderen Website interpretieren würde.

namespace App\Controller;

use App\Model\Product;
use DateTimeImmutable;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

#[Route(methods: ['GET'])]
class PagesController extends AbstractController
{
    #[Route('/', name: 'home')]
    public function home(): Response
    {
        return $this->render('pages/home.html.twig', ['name' => 'Marie',
            'today' => new DateTimeImmutable('2026-09-23')]);
    }

    #[Route('/products', name: 'products')]
    public function products(): Response
    {
        return $this->render('pages/products.html.twig', ['products' => [
            new Product('Keyboard', 2500),
            new Product('Mouse', 1250),
            new Product('Screen', 114900),
        ]]);
    }
}

    Die Aktionen sind sprachunabhängig: Sie liefern Rohdaten (einen Namen, ein Datum, Beträge in Cent). Übersetzung und Formatierung übernehmen die Views. Die Klasse [Product] hat einen Namen und einen Preis in Cent; die Erweiterung [FormatsExtension] ist die aus Beispiel 16: Ihr Filter [long_date] schreibt ein Datum im „vollständigen“ Format der Anfragesprache („Wednesday, September 23, 2026“, „mercredi 23 septembre 2026“), und ihr Filter [money] schreibt einen Betrag.
